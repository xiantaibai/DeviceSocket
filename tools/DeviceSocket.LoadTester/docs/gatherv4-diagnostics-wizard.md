# GatherV4 五万设备连接压测：选项 8 使用教程

> **旧版兼容文档**：选项 8 会同时组织资源、PerfView、Dump 和多个状态窗口，已经不再推荐用于日常压测。新的单窗口入口见 [GatherV4 压测服务器轻量监控](gatherv4-simple-monitor.md)；本页只在需要复现旧流程时使用。

**从选项 8 开始：配置一次，自动打开资源、PerfView、Dump 三个状态窗口。**

本教程按你的当前环境举例：老版本 GatherV4、连接端口 `8890`、两台压测机合计五万设备。TcpCenter 不参加本次压测。

操作顺序：**服务器选 8 → 填本轮信息 → 选服务 → 等全部就绪 → 手动启动压测 → 异常按 D / 正常结束按 Q → 保存结果。**

## 1. 第一次使用，准备什么？【手动，只需配置一次】

把下面四个脚本放在**被测服务器**同一个目录，例如 `D:\GatherDiagnostics`：

```text
D:\GatherDiagnostics\
  Start-GatherV4Diagnostics.ps1
  Invoke-GatherV4Diagnostics.ps1
  GatherV4.IncidentCapture.ps1
  Watch-GatherV4Monitor.ps1
```

用记事本打开 `Start-GatherV4Diagnostics.ps1`，找到顶部的这段配置，填入服务器已经安装好的工具位置：

```powershell
$configuredToolPaths = @{
    PerfViewPath = 'C:\Tools\PerfView\PerfView.exe'
    ProcDumpPath = 'C:\Tools\ProcDump\procdump64.exe'
}
```

这是路径示例，**要改成你服务器上的实际路径，包含 exe 文件名**。已经维护好的可跳过；工具不用重装，以后每轮也不用再输入路径。更新脚本时四个文件一起替换，并把原来的工具路径填回。

手动确认保存结果的磁盘有足够空间，能容纳三份完整 Dump 和性能跟踪文件。

## 2. 怎么打开？【手动】

在被测服务器打开**管理员 PowerShell**，执行：

```powershell
& 'D:\GatherDiagnostics\Start-GatherV4Diagnostics.ps1'
```

看到“这个窗口现在要做什么？”时，**输入 `8`，再按回车**。

**这一题一定输入 8。当前脚本初始默认是 1，直接回车可能进入单独资源记录。**

后面显示了正确默认值的问题，可以直接回车；正在回答问题时输入 `q` 会退出。

如果看到“这个新窗口是否继续当前这一轮？”，这样选：

| 你现在要做什么 | 输入 |
| --- | --- |
| old-r2 已经结束，现在开始 old-r3 | **3：开始新一轮** |
| 本轮只是重新打开向导，继续使用相同设置 | **1：沿用本轮数据** |
| 本轮不换 RunId，只改服务或采集参数 | **2：同一轮修改** |

首次使用没有保存过设置，就不会出现这个问题。选 1 会跳过已经保存的问答，直接让你核对摘要；正在运行的监控不会因另一个窗口修改设置而改变。

## 3. 本轮信息怎么填？【手动】

下面以老版本五万连接的下一轮 `old-r3` 为例：

| 向导问题 | 本次填写 |
| --- | --- |
| 这轮正在压测哪个场景？ | **2：五万连接** |
| 服务器当前实际运行哪个版本？ | **1：老版本 old** |
| 本轮 RunId 是什么？ | `gatherv4-connections-50000-old-r3` |

RunId 就是**这一轮测试的名字**。服务器监控和两台压测机必须用同一个名字，之后才能把结果对上。下一轮用 `old-r4`，不要继续写到已经完成的 old-r3 目录。

**注意：选场景只给监控文件做标记，不会启动五万设备，也不会修改 LoadTester 参数。**

## 4. 监控哪些服务？怎样避免选错重名进程？【手动确认】

### 先选 ConnectService

按下面顺序操作：

1. “如何确认要监控的实例？”输入 **1：输入监听端口**。
2. “本机监听端口是多少？”输入 **8890**；只有本轮确实用 8890 时才接受这个默认值。
3. 核对列表里的**程序路径、服务名、当前 PID**，选择本轮 GatherV4 对应的编号。

同名 exe 可能属于不同环境，不能只看名字或 CPU 高低。列表编号会变，按本次显示选择；截图里的旧 PID 不要照抄。

### 再加入同环境的其他服务

“是否再添加其他本机服务？”选 **2：继续添加**，再选 **2：从 Gather 服务列表选择**。可以输入多个编号，例如 `1,3`，但要按本次列表核对。

| 对象 | 本次怎么处理 |
| --- | --- |
| ConnectService，监听 8890 的实例 | **必须加入；主要 Dump 对象选它** |
| 同环境 DirectiveService | 加入资源记录 |
| 同环境 TimerTaskService / 采集任务中心 | 加入资源记录；未运行也可选择，启动后自动记录 |
| 同机运行的相关 IIS/API，例如上轮出现的 AfterSaleApi | 确认实际进程后加入资源记录，帮助判断是否抢占服务器资源 |
| TcpCenter | **不要加入** |

服务列表中找不到任务中心，可改选 **3：输入 Windows 服务内部名称**。不是显示名称；内部名称以服务属性为准。

IIS/API 不在服务列表时，需要你**手动核对应用池或后端进程**，再选 **4：输入已确认的 PID**。不要随便选全部 `w3wp.exe`，也不要选 PID 4；PID 4 不是具体业务应用。此五万连接场景没有额外 HTTP 压测，加入 API 是为了观察同机资源竞争。

加完后，“是否再添加其他本机服务？”选 **1：选好了，继续**。

### 采集参数怎么填？

首次配置选项 8 时，下列值可以直接接受默认：

| 问题 | 默认值 | 通俗解释 |
| --- | --- | --- |
| 一键监控最多持续多少秒？ | `14400` | 最多监控 4 小时；不代表压测必须跑 4 小时 |
| 资源记录间隔多少秒？ | `2` | 每 2 秒记录一次 CPU、内存等 |
| 按 D 后每份 Dump 写完间隔多少秒？ | `10` | 写完一份，等 10 秒，再写下一份，共三份 |
| 整机 Thread 循环跟踪保留大小 MB？ | `2048` | PerfView 使用约 2 GB 循环记录，保留最近一段活动 |

沿用本轮设置时不会重复询问，**以最后摘要显示的实际参数为准**。想改参数，重新运行向导并选“2：同一轮修改”。

“异常时主要给哪个进程抓三份 Dump？”选择**刚确认的 Connect8890**。其他已选服务记录资源，不会一起抓三份 Dump。

“采集文件保存到哪个根目录？”可以使用 `D:\GatherEvidence`，或填写你准备好的磁盘目录。

核对最后摘要里的 RunId、服务路径、当前 PID、工具路径、时长和输出目录。正确后选 **1：开始执行**。选 **2：仅预览**只是看命令，不会开始监控。

## 5. 什么时候启动五万设备？【必须手动】

确认开始后，脚本自动启动采集，并打开三个状态窗口：

| 窗口 | 你能看到什么 | 要不要在里面输入命令？ |
| --- | --- | --- |
| 主窗口，也就是刚才回答问题的窗口 | 是否全部就绪、取证进度、结束结果 | **异常按 D，正常结束按 Q** |
| 资源状态窗口 | 服务 PID、CPU、内存、线程、句柄及采样时间 | 不用，只看状态 |
| PerfView 状态窗口 | 是否采集中、是否正在保存、工具日志 | 不用，只看状态 |
| Dump 状态窗口 | 是否在监听、是否开始抓取、Dump 文件情况 | 不用，只看状态 |

**三个窗口打开不等于采集已经就绪。等主窗口明确显示“全部采集已就绪”，再开压测。** 如果显示报错或未就绪，先处理提示，不要先启动负载。

然后去**两台压测机，手动启动原来的五万连接命令**：

- 两台都把 `--run-id` 改为 `gatherv4-connections-50000-old-r3`。
- 按你目前 old-r2 的两分片方式运行：`--shard-count 2`，第一台 `--shard-index 0`，第二台 `--shard-index 1`，每台约 2.5 万设备，合计五万。
- 其余场景配置、完整设备 CSV 和启动方式沿用原测试，两台使用相同的约定启动时间。

仓库场景文件默认写的是四分片；本教程按你已有的**两分片**操作。实际运行参数要核对，不能一台用 2、另一台用 4，也不是每台各启动五万设备。

**选项 8 不会替你启动 LoadTester，也不会部署版本或启动、停止业务服务。** 不需要另外再开选项 1、2、5。

## 6. 压测时怎么操作？

### 心跳停滞、批量掉线：手动按 D

持续观察负载机日志。出现心跳确认长时间不再增加、在线数明显下降或业务持续不响应时：

1. **先回到监控主窗口，按 D。** 确保键盘焦点在主窗口，不是在三个状态窗口。
2. 先保留现场，不要先重启 Connect、停止业务服务或取消压测。
3. 等脚本完成取证，出现“组合诊断结束”和证据目录。完整 Dump 写入和 PerfView 保存可能需要等待。
4. 记录你观察到的异常时间，再按测试安排手动结束负载或进行恢复。

按 D 后，脚本自动保存异常前的 PerfView 跟踪，安全取消退出监听，再抓三份 Connect 完整 Dump，最后保存资源和事件记录。**按 D 完成后，这次监控会结束；如需继续监控，要重新运行向导。** 若 Connect 已退出或换 PID，可能无法抓齐三份，仍应保存已有结果。

**心跳停滞不是自动触发条件。当前没有压测机共享目录，需要你看到异常后手动按 D。选项 8 也不会因为 CPU 或内存达到某个阈值就自动抓三份 Dump。**

### Connect 自己退出或出现未处理异常：自动尝试取证

退出监听会自动尝试抓一份完整 Dump 并保存跟踪，不需要先按 D。保留结果，记下异常时间以及是否有人操作服务；正常人为停止也可能触发退出 Dump，不能只凭有 Dump 就认定崩溃。

### 正常跑完：手动按 Q

负载机完成本轮测试和连接清理后，在**主窗口按 Q**。脚本保存跟踪、资源和事件，然后结束；没有故障时不额外抓三份存活 Dump，没有 DMP 也可以是正常结果。

不要直接点主窗口右上角关闭按钮。Ctrl+C 是取消监控并保留已有结果，**不是抓三份 Dump**；正常收尾优先用 Q。

单独关闭某个状态窗口，只会关闭显示，采集还在继续；主窗口结束后，状态窗口显示最终结果并自动关闭。

## 7. 结果在哪？需要保存哪些文件？【手动归档】

例如使用 `D:\GatherEvidence`，本轮结果在：

```text
D:\GatherEvidence\old\gatherv4-connections-50000\gatherv4-connections-50000-old-r3\服务器名\
```

实际路径以主窗口显示为准。**整个目录一起保存，不要只挑一份 Dump。**

| 文件 | 可以用来查什么 |
| --- | --- |
| `*-incident.json` | 本轮对象、就绪和触发时间、最终状态、文件清单 |
| `.etl` / `.etl.zip` 与 PerfView 日志 | CPU 消耗、线程等待和跟踪是否成功保存 |
| `.dmp` | 内存及线程现场；按 D 通常三份，自动退出取证通常一份 |
| 资源 `.csv` 与 `*-sample.json` | CPU、内存等变化和实际采样时间 |
| 身份、事件及 ProcDump 日志 | 是否换过进程、服务退出和工具执行情况 |

还要手动收集**两台负载机的同一 RunId 结果目录**，和服务器监控结果一起保存。发生异常时把观察时间、按 D 时间、停止负载时间记下来；已有部分结果也保留，不因取证未抓齐而丢弃。

## 8. 下一轮，或者换优化版，怎么做？【手动】

先让上一轮监控和负载正常结束，再重新运行向导：

```text
这个窗口现在要做什么？ → 8
这个新窗口是否继续当前这一轮？ → 3：开始新一轮
这轮正在压测哪个场景？ → 2：五万连接
服务器当前实际运行哪个版本？ → 老版选 1；优化版选 2
本轮 RunId 是什么？ → 新一轮名称，两台负载机也同步修改
```

例子：下一轮老版可用 `gatherv4-connections-50000-old-r4`；优化版首轮可用 `gatherv4-connections-50000-optimized-r1`。

**部署优化版需要你手动完成。向导里选“优化版”只是标记文件，不会替换服务程序。** 每轮重新确认端口和部署路径，PID 变化由向导重新查询，不照搬旧 PID。

老版与优化版比较时，保持五万设备、设备 CSV、两台分片、建连速度、心跳设置、服务器条件和监控参数一致。完整 Dump 会暂停目标，按 D 的取证时段用于排查，不当成正常性能数据；PerfView 循环文件只保留最近一段，不能当成四小时完整记录。

## 9. 遇到这几个情况怎么办？

| 情况 | 怎么处理 |
| --- | --- |
| 提示工具不存在 | 检查脚本顶部的实际 exe 路径；临时输入替代路径只在本次生效 |
| 端口 8890 找不到实例 | 确认在 GatherV4 服务器执行、Connect 已启动、当前测试端口确实是 8890；不要随便改选同名进程 |
| 按 D/Q 没反应 | 先点击主窗口再按；远程控制台不支持按键时，照抄主窗口显示的本轮请求命令，在同一服务器另一个 PowerShell 执行；Capture 等同 D，Finish 等同 Q |
| 已有一键监控正在运行 | 回到原主窗口操作，不要重复启动第二套监听 |
| 不想显示三个状态窗口 | 启动命令末尾加 `-NoMonitorWindows`，采集和主窗口 D/Q 操作不变 |
| 服务重启或 IIS 回收换了 PID | 重新运行向导确认对象并布置；主要 Dump 监听不会自动绑定新 PID |

首次把本包部署到服务器时，先做一次短演练：**选 8 → 等全部就绪 → 按 Q → 核对最终状态及可用 ETL/ZIP**，再开始正式复测。本机已验证窗口和 ProcDump 流程，真实 PerfView ETW 仍需在服务器管理员环境确认。

其他选项和手动命令需要时再查 [进阶操作手册](gatherv4-perfview-dump-runbook.md)。
