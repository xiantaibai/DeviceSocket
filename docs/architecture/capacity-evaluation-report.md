# DeviceSocket 容量与架构评估报告

> 目标：8 核 16G 服务器单节点支撑 8～10 万设备连接，指令采用"一问一答"可靠模型（设备 A 的 A2 消息必须等 A1 收到回复后才能发送），允许消息重试并保证通讯质量；最终演进到百万设备。

## 一、结论速览

| 评估维度 | 结论 | 置信度 |
| --- | --- | --- |
| 一问一答可靠消息模型 | ✅ 架构已完整实现（设备级唯一执行通道 + 状态机 + 重试 + 确认） | 高（代码/文档/测试齐备） |
| 8～10 万单节点连接 | ⚠️ 代码层按 6～8 万设计，连接硬上限 85,000，**未在目标环境实测到 8～10 万** | 中（无实测数据支撑） |
| 百万设备目标 | ✅ 架构预留（1024 固定分片、多 Gateway + 多 Silo 横向扩展） | 中（仅容量不变量测试，无端到端实测） |
| 通讯质量（重试 + 幂等） | ✅ 三重复试 + 协议级 PSEQ 幂等 + MsgId 幂等，设计完备 | 高 |
| 生产就绪度 | ❌ 尚未达到（缺多 Silo 故障演练、缺认证/TLS、缺 OpenTelemetry、缺 6 万+ 长稳） | 高（文档自述） |

**一句话结论**：一问一答可靠消息的核心语义（串行、重试、确认、幂等）已经在 Orleans 层和 Gateway 协议层完整落地，这是本项目最强的部分；**主要不足集中在"容量未被实测验证"和"生产化配套缺失"两块**，其中单节点 8～10 万连接是目前最大的不确定性来源。

## 二、当前架构与一问一答模型评估

### 2.1 整体架构

```text
业务服务 ── Orleans Client ──> IDeviceGrain ──> IDeviceCommandGrain
                                    │                   │
                                    │ 一问一答通道      │ 到期唤醒
                                    ▼                   ▼
                          GatewayNodeGrain ──MagicOnion──> DeviceSocket.Host (SuperSocket)
                                                            │ 真实 Socket
                                                            ▼
                                                          设备 A (376.1 / 645)
```

关键分层与职责（与 AGENTS.md 规则一致）：

- **Gateway（DeviceSocket.Host）**：SuperSocket 承载真实 TCP 连接，进程级连接限额、Session 生命周期治理、协议拆包/编解码、指令 Handler 分发、命令应答关联（PSEQ 匹配）。
- **Orleans Cluster（Silo）**：设备路由、网关租约、可靠命令状态机、分片调度器，全部可序列化状态持久化到 SQL Server。
- **MagicOnion（HTTP/2 7001）**：Gateway 与 Silo 之间的内部 RPC 下发通道。
- **SQL Server**：设备/命令/网关/调度四类独立应用表 + Orleans ADO.NET 集群成员与 Reminder。

### 2.2 一问一答模型实现评估（核心诉求）

用户诉求"给设备 A 发送 A1、A2，A2 必须等 A1 回复后才能发送，且保证通讯质量、允许重试"——这正是 `IDeviceGrain` 可靠命令的设计目标，实现完整：

1. **设备级唯一执行通道**：`DeviceGrain` 内 `ActiveCommandId` 同一时刻只允许一条命令占用"等待回复"通道（`DeviceGrain.cs` 的 `ProcessWorkAsync`），A2 在 A1 进入终态前不会下发。✅
2. **可靠持久化与状态机**：`DeviceCommandGrain` 完整状态机 `EnqueuePending → Queued → Dispatching → AwaitingConfirmation → RetryPending → Confirmed/Expired/Failed/Cancelled`。✅
3. **重试与通讯质量**：
   - 三级退避（默认 1s / 3s / 10s / 30s），默认最大 5 次尝试、回复超时 10s、整体 TTL 5 分钟。
   - 明确失败 → 递增 AttemptNo 重试；结果不确定（Gateway 调用异常/写入失败但终端可能已收）→ **复用同一 AttemptNo** 避免重复副作用。
   - 协议级幂等：376.1 为新 MsgId 分配 PSEQ 并强制 `CON=1`，同 MsgId 重试复用 PSEQ；终端按"同主站地址 + 同 Session + 同 PSEQ + 同 AFN/DA/DT"幂等去重。✅
4. **确认闭环**：Gateway `AFN=00H/F3` 逐数据单元确认，通过 `Session + PSEQ + 原 AFN/DA/DT + 回复截止时间` 五重匹配后才提交 Orleans，迟到/重复/错配响应直接丢弃。✅
5. **故障恢复**：Silo 退出后由 1024 个固定分片调度器通过 Reminder + SQL 索引幂等恢复；Gateway 崩溃的"部分写入"不确定边界通过复用 AttemptNo + 终端缓存结果解决。✅

**结论**：一问一答 + 重试 + 质量保证这一核心诉求，架构与实现层面已达标，且经过真实 Orleans TestingHost 集成测试覆盖（设备串行、重试、取消、过期、旧 Session、恢复状态机）。

## 三、目标 vs 现状差距分析

### 3.1 单节点 8～10 万连接：最大不确定性

**现状**：
- 连接硬上限 `MaxConnections = 85000`，文档明确"为 80,000 条目标连接预留余量"——**代码目标锁定在 8 万，未覆盖 10 万**。
- 文档《production-readiness-plan.md》第 227 行明确：**"6 万连接需要在独立 8 核 16 GB 环境分阶段压测，本地开发阶段以业务链路通畅和异常隔离为目标"**。
- 仓库现有压测报告（`load-test-results/` 下的 `gather-http-reading-50000`、`gather-reconnect-storm-50000`）**实测对象是 Gather.TcpCenter / GatherV4 老服务**，不是 DeviceSocket.Host 自身。DeviceSocket 自己的 TCP 层 5 万+ 连接长稳**尚无实测记录**。

**关键风险点**：

| 风险 | 说明 | 影响 |
| --- | --- | --- |
| 无 8～10 万实测 | 8 核 16G 下 CPU/GC/Socket 内存/文件描述符/线程池的真实瓶颈未知 | 无法承诺容量 |
| 连接上限 85000 | 若要 10 万需提高上限并重新评估内存 | 需改配置 + 压测 |
| Socket 缓冲内存 | 4KB 收发缓冲 × 10 万 ≈ 每方向 400MB，加上内核 socket 结构、SessionEntry 对象开销 | 16G 内存需精细测算 |
| 心跳写放大 | `OrleansDeviceRoutePublisher` 单线程消费、有界队列 65536（`DropWrite` 满则丢弃）；10 万设备 × 120s 心跳 ≈ 833 次/秒 Touch，路由持久化虽合并到 30s，但 Orleans Grain 调用本身仍是逐条 RPC | 心跳峰值可能成为瓶颈 |
| 集中重连 | 5000 连接/秒接入限速 + 128 并发关闭，重连风暴时能否快速恢复未知 | 需故障注入验证 |

### 3.2 百万设备目标：架构预留到位，端到端未验证

**架构侧已就绪**：
- 固定 1024 分片调度器（`SchedulerShard = StableHash(DeviceId) & 1023`），Reminder 数量恒定不随设备增长。✅
- `DeviceCommandCapacityInvariantTests` 对 100 万设备编号做稳定哈希，验证分片覆盖与热点边界。✅
- 多 Gateway 承载连接 + 多 Silo 承载状态，Gateway 与 Silo 独立扩展。✅
- SQL 结构化索引列避免百万设备全表扫描（设备到期索引、队列索引、恢复索引）。✅

**未验证 / 未完成**：

| 缺口 | 说明 |
| --- | --- |
| 心跳逐条 RPC | 文档自述："Gateway 仍会把设备活动逐条调用到 Orleans；百万在线设备的最终吞吐还需要后续在 Gateway 合并或批量发布活动事件"（cluster-and-rpc.md 第 171 行） |
| 多 Silo 故障演练 | 阶段二"多 Silo 故障演练、生产备份恢复和容量压测仍需在部署环境完成" |
| 百万设备端到端压测 | 仅有 100 万编号的哈希不变量测试，无 100 万在线设备 + 命令下发实测 |
| 路由事件可丢弃 | 路由队列满 `DropWrite`，虽靠租约兜底，但百万规模下丢事件影响待评估 |

### 3.3 生产化配套缺失（与目标间接相关但必需）

摘自项目自述（production-readiness-plan.md），当前 Demo 边界：

1. **API / Swagger / MagicOnion 无认证与 TLS**（阶段四未实施）。
2. **协议响应关联已接入 376.1 F3，但查询类命令（需返回业务数据）的专用响应 Handler 未做**（只有确认型闭环）。
3. **无 Outbox / Kafka 上报异步化**（阶段六未实施）——目前设备上报的标准化事件分发到业务侧是同步/未完成的。
4. **无完整健康检查、OpenTelemetry、集中告警**（阶段五未实施）。
5. **Orleans 生产存储**：代码已切 SQL Server，但"生产数据库仍需执行官方 Membership/Reminder 初始化脚本并完成多 Silo 实际部署演练"。
6. **无 6 万+ 连接长稳、重启、故障切换验证**。

## 五、结论与建议

### 5.1 总体判断

- **一问一答可靠消息模型：完全支持**，这是项目最成熟的部分，语义、幂等、重试、恢复均已闭环并有集成测试。
- **单节点 8～10 万连接：尚不能认定支持**。代码目标锁定 6～8 万（上限 85000），且从未在 8 核 16G 环境实测；要承诺 8～10 万，必须先完成目标环境分阶段长稳压测。
- **百万设备：架构方向正确、可演进**，但心跳上报的逐条 RPC 是明确的技术债，且端到端未验证。

### 5.2 优先级建议（若要达成目标）

1. **【P0】完成 8 核 16G 目标环境的分阶段压测**（1 万 → 3 万 → 6 万 → 8 万 → 10 万连接），按 `linux-single-node-load-test.md` 执行，实测 CPU/GC/Socket 内存/文件描述符/线程池瓶颈。这是判断"能否支持 8～10 万"的唯一依据。
2. **【P0】确认连接上限与内存预算**：若需 10 万，提高 `MaxConnections` 并重新测算 Socket 缓冲 + SessionEntry 对象内存是否在 16G 内。
3. **【P1】心跳/活动上报批量化**：解决"逐条 RPC 到 Orleans"的写放大，否则百万设备心跳会成为瓶颈（对单节点 8～10 万同样重要）。
4. **【P1】补齐生产化**：多 Silo 故障演练、认证/TLS、OpenTelemetry + 告警、健康检查。
5. **【P2】查询类命令响应 Handler**、Outbox/Kafka 上报异步化、命令死信重放。

### 5.3 一句话给决策

**"可靠指令一问一答 + 重试 + 幂等"已经做扎实了；"单节点 8～10 万连接"目前只有代码设计没有实测背书，是上线前必须先补的功课；百万设备方向正确，但心跳上报的逐条 RPC 是必须先拆的雷。**
