# DeviceSocket 通讯服务中心生产化改造计划

更新日期：2026-09-07。目标为系统总在线 80,000～100,000 台设备。

本计划基于当前代码审查和通讯服务中心职责重新编排，替代旧版以通信 Demo 为中心的阶段顺序。项目背景、独立看板范围、六种发送组合和接口草案统一见 [项目背景](project-background.md)。本文的待办均为规划，不能据此认定功能已交付或容量已验证。

## 1. 项目目标与实施边界

通讯服务中心负责设备消息上行转发、业务指令下行投递和指令结果回传。核心交付同时包含通讯执行能力与独立监控看板，覆盖设备归属、单设备指令日志、队列积压和命令速度。

业务系统负责业务规则和决定发送目标、内容及时间。通讯中心提供单条/批量的立即、延后、指定时间单次发送，以及持久化、设备级一问一答、超时过期、重试、查询与取消。周期性业务任务的生成保持在业务系统，后续托管循环计划时单独扩展契约。

继续保留 Gateway、Cluster、Shared 和 Infrastructure 的部署/代码边界。Socket 只在 Gateway 内存中；Orleans 管理可序列化状态；接入 API 复用 IDeviceGrain；查询模型、日志和监控指标服务独立看板。新服务按部署边界放入 src 对应分组，HTTP API 统一由 DeviceApiEndpoints 注册，Program.cs 只负责宿主配置和注册。

已确认的代码风险需要进入第一批修复：HTTP 直接写 Socket 绕过设备通道；SQL 队首查询过滤过期 Queued 项却未见主动终态扫描；ConfirmAsync 缺独立截止时间校验；Gateway RPC 未显式设置 deadline；回包提交失败只释放匹配权；去重辅助队列在持续失败时可能不断增长；上行日志在匹配前生成新 MsgId。

这些是静态审查发现，不是本次已经完成的故障复现或压测结果。

## 3. 必须统一的语义

### 3.1 受理、发送与完成

- 单条成功受理必须以可靠状态持久化为前提；HTTP 202 不是设备执行成功。
- 批次成功受理表示批次清单可恢复；子项受理、拒绝和执行进度独立记录，不伪装成跨设备原子事务。
- 写入 Socket、协议确认、业务数据返回和向业务系统投递成功分别记录；无法从协议判断业务执行结果时应如实展示。
- 同一设备所有业务命令共用唯一执行通道；不同设备有界并行。立即发送不抢占正在等待应答的命令。
- 普通消息只尽力即时发送，不创建可靠状态或自动重试；延后/定时业务任务必须使用可靠入口。

### 3.2 时间与幂等

- 立即、相对延后和指定时间单次发送，统一转换为首次受理时持久化的 NotBefore；ExpiresAt 是固定绝对截止时间，ReplyDeadline 不得越过它。
- 新 API 在未显式传 expiresAt 时，按计划发送时刻加 ttlSeconds 计算有效期；旧 Orleans 调用的默认 TTL 行为保持兼容，适配层显式传值。字段约束见项目背景，不在本次修改运行配置。
- MsgId、BatchId 和子项身份稳定；相同身份重复受理返回原结果，不重新计算延后、有效期或展开子项。截止时间和调度策略纳入内容幂等检查。
- 到期后不再开始新发送；排队项自动转为 Expired。已经发出的指令可能已执行，取消不能承诺撤回设备动作。
- 确认使用可信 Gateway 接收时间、AttemptNo、SessionEpoch 和协议关联字段验证；终态不可被迟到回包覆盖。持久化回包晚于超时处理到达时的裁决和审计规则必须测试。
- 相同逻辑命令上下行及跨服务调用复用 MsgId/TraceId，以 Direction 区分方向；批次关系单独用 BatchId/ItemId 表达。

### 3.3 在线、日志与故障隔离

- Gateway 本地 Socket 是连接事实来源，集群路由是可恢复索引。登录/续租/断开通过版本与对账最终一致。
- 设备心跳、路由续租、节点租约、协议空闲回收的周期要组合校验，避免物理在线而业务路由频繁过期。
- 程序日志和通信日志用于定位问题，关键受理、命令结果和转发记录需要可靠持久化。
- 数据库、业务系统、日志平台或 Collector 故障时必须维持有界资源，分别实施拒绝、背压、暂存和恢复策略；不能一概无限缓冲或静默丢失。

## 4. 阶段 A：职责和对外契约冻结

本阶段先落实用户可理解、开发可实施的通讯能力与看板口径，优先级 P0。

- [ ] A1：以项目背景为基准确认通讯中心、业务系统、协议适配、查询与看板职责，形成目标组件和部署边界。
- [ ] A2：冻结设备上报与命令结果事件契约，明确 SchemaVersion、事件幂等身份、业务归属、顺序要求、投递确认、重试/死信和数据保留。
- [ ] A3：冻结单条与批量受理、状态、子项查询和取消接口；覆盖立即/延后/定时六种组合及稳定错误码，生成 OpenAPI 草案。
- [ ] A4：确定单批条数/字节、每设备积压、业务系统和节点配额、预约范围、TTL 上限及授权优先级，确保每项都有验证和拒绝语义。
- [ ] A5：冻结独立看板页面、数据源、在线/Socket/积压/速度口径和权限；确定首期业务投递适配器。

交付：项目背景、接口与事件契约、限额表、看板页面清单和验收指标。示例接口为 POST /api/v1/devices/{deviceId}/commands 与 POST /api/v1/command-batches，通过 schedule.mode 复用同一套执行逻辑。

验收：六种发送组合、上报和结果回传均有具体输入、受理含义、查询方式和失败语义；“命令速度”明确区分受理、物理发送、协议确认与业务完成。

## 5. 阶段 B：接通生产链路与正确性修复

优先级 P0。最小指标与日志关联随修复同步接入，后续容量调优依赖这些数据。

- [ ] B1：Gateway 接入生产集群发现并对齐 ClusterId/ServiceId、节点身份和可达地址；保留明确的本机开发模式，生产禁止静默使用单机默认值。
- [ ] B2：业务 HTTP 下发统一进入 IDeviceGrain；直接 Socket 调试能力隔离、授权并禁止绕过活动业务命令。保留统一 Send 命名。
- [ ] B3：路由事件按 DeviceId 分片、同设备有序消费；活动合并；登录/断开补偿；增加真实丢弃回调、深度、最老等待和延迟指标。
- [ ] B4：周期对账恢复登录与路由，校验当前 Session 和实例，防止旧 Gateway 事件覆盖新连接；联动心跳、设备租约和节点租约。
- [ ] B5：补已过期排队指令扫描和终态收敛，避免 SQL 过滤后无人处理；确认和最终发送位置补截止时间校验与剩余预算。
- [ ] B6：为 Gateway RPC 增加 deadline、取消传播、并发预算与退避抖动，明确确定失败、结果不确定及非幂等指令重试策略。
- [ ] B7：修复 Gateway 去重字典与辅助队列生命周期，增加有效期、内容一致性和容量治理；去重保留期与最大重放窗口一致。
- [ ] B8：补 376.1 查询类应答、645 业务应答、多帧合并及异常码；验证 PSEQ 回绕和迟到重放，协议无法区分时限制复用窗口并说明边界。
- [ ] B9：设备回包增加持久化暂存和自主重投；调用 DeviceGrain 验证当前命令/会话后推进 CommandGrain，避免绕过设备通道。
- [ ] B10：在响应匹配后使用原 MsgId/TraceId 记录上行通讯日志；持久化命令应答结果及每次尝试事件。

交付：可靠下发/应答闭环、路由对账、过期扫描、回包恢复、统一日志身份及专项测试。

验收：同设备不并行等待业务应答；旧 Session 不确认新命令；无人查询时排队过期也会终态；路由和回包故障后能自动恢复；持续失败下去重缓存和各队列有界。

## 6. 阶段 C：上行转发、结果回传与六种发送组合

优先级 P0。上报转发由旧版后置阶段提前为通讯中心首期核心能力。

- [ ] C1：协议 Handler 输出标准事件，将持久化上行转发、消息路由和业务投递从 TCP 收包路径中隔离；按业务目的地和设备维护所需顺序。
- [ ] C2：实现持久化转发记录/Outbox、后台投递、幂等确认、退避、死信和受控重投。存储与下游故障时执行限额、背压和可观测拒绝。
- [ ] C3：命令结果与结果投递记录保持原子关联或可恢复补偿；业务系统可按 MsgId 查询或接收结果事件，投递失败不重新触发设备命令。
- [ ] C4：实现单条模式化受理接口，将立即/延后/定时归一为持久化时间；严格验证模式互斥、时区、延迟、到期和请求幂等。
- [ ] C5：实现同设备批量与跨设备持久化批次，保存 BatchId、ItemId、子 MsgId、原始顺序、清单、展开游标和逐项结果。
- [ ] C6：批次分块展开，限制全局/节点/业务系统并发与速度；同设备始终串行；同一时刻大量预约通过预算执行，记录实际调度延迟。
- [ ] C7：服务重启恢复批次游标和预约；已到时未过期的继续，已过期的终止，幂等重放不创建重复子项。
- [ ] C8：实现单条/批次状态、子项游标分页和取消；冻结批次后阻止新的展开，发送与取消竞态由持久化状态裁决。
- [ ] C9：建立设备路由、命令历史、响应结果、批次和转发结果的索引查询模型；避免历史查询大量激活 Grain 或反序列化原始 Payload。

交付：业务接入 API、上行/结果投递适配器、预约发送、批次协调与查询能力；接口端点和数据字段详见项目背景。

验收：六种组合均可受理、执行、跟踪和取消；同设备不插队；跨设备部分失败逐项可查；批次重放/服务重启不重复展开；上行与结果投递在下游恢复后按约定继续且可对账。

## 7. 阶段 D：独立监控看板、集中日志和 OTel

优先级 P1，正式上线前必须完成。阶段 A 冻结的查询接口和最小观测先行，完整页面依赖阶段 C 的查询模型。

- [ ] D1：交付独立看板访问入口、登录和发布配置，包含集群总览、Gateway、Silo/调度、设备、单设备日志、命令、批次、转发与告警页面。
- [ ] D2：展示在线设备数和 Socket 数的不同口径、未认证数、各类队列深度/最老等待、命令各阶段速度、成功率和 P95/P99 延迟。
- [ ] D3：提供设备到 Gateway NodeId/InstanceId/SessionEpoch 的定位；指令日志保留发生时节点，设备迁移后仍可跨节点检索。
- [ ] D4：实现聚合查询、分页、时间范围和缓存/限流；每次看板刷新不得遍历十万个 Grain，缺失或过期数据明确显示状态和采集时间。
- [ ] D5：Gateway/Silo/接入和转发模块接入 OTel SDK、ActivitySource、Meter 与 OTLP；订阅 Microsoft.Orleans 和 DeviceSocket.Cluster.Commands，补 Gateway 和命令当前状态指标。
- [ ] D6：跨 HTTP、Orleans、MagicOnion、持久化调度与回包传播 W3C 上下文；每次尝试使用独立 Span，沿用原 TraceId；不为长连接创建长期不结束的 Span。
- [ ] D7：Gateway 和 Silo 日志统一结构化、节点/版本字段与 TraceId/SpanId；集中采集程序及上下行日志，支持单设备临时诊断、授权查看和保留期限控制。
- [ ] D8：为日志和 Collector 建立缓冲、导出失败、采样和磁盘告警；Trace 采样不能替代关键指令状态和结果持久化；错误尾采样需验证容量和完整性。
- [ ] D9：建立在线异常下降、路由积压、命令超时/过期、调度滞后、转发死信、SQL 失败、日志丢弃和节点失联告警，并给出处理指引。

交付：可独立访问的通讯运维看板、查询 API、集中日志、Collector 配置、指标/Trace 接入和告警规则。基础设施时序面板不能替代设备和命令查询页面。

验收：输入任一测试 DeviceId 可定位真实 Gateway、当前与历史指令；输入 MsgId 可串起上下行、尝试、结果和业务投递；批次部分失败可下钻；时序指标不使用 DeviceId/MsgId/TraceId 高基数标签；观测后端故障不阻塞通讯主链路。

## 8. 阶段 E：高可用、资源预算与部署治理

优先级 P1。生产上线门槛的一部分，不以单机纯在线压测替代。

- [ ] E1：完成多 Gateway、多 Silo 和生产数据库部署；按实测单节点容量及故障后余量确定节点数，验证唯一身份、租约和跨节点路由。
- [ ] E2：建立每连接真实内存、内核 Socket、FD、CPU/GC、发送积压和新连接速率预算；复核 85,000 配额与十万总在线目标的关系。
- [ ] E3：测量每条命令 SQL 读写次数、连接池等待、索引执行计划和事务日志压力；限制调度恢复与历史清理的总并发，避免 1024 分片放大存储负载。
- [ ] E4：按指令频率核算状态、尝试历史、原始报文和转发日志容量。复核当前 Payload 7 天/命令 30 天及文件数量保留策略，幂等重放窗口与物理清理联动。
- [ ] E5：实现 /health/live、/health/ready 和节点 Starting/Ready/Draining/Stopped。就绪按接入/下发/查询能力评估；日志或 Collector 故障以降级和告警处理，不默认让所有节点退出服务。
- [ ] E6：排空时停止新接入与新的指令执行，持久化保留未完成任务，再按预算处理在途通信和断链；现有 TCP 连接迁移依赖设备重连，不承诺连接无损转移。
- [ ] E7：看板/业务 API 接入认证、RBAC、业务系统目标授权和审计；内部 RPC 使用 TLS 与服务身份；限制请求体、查询范围、调用频率和原始报文访问。
- [ ] E8：交付 Gateway/Silo/API/看板/转发/Collector 的部署配置、数据库迁移、备份恢复、滚动发布与回滚手册；完成契约和状态版本兼容测试。
- [ ] E9：持续集成执行格式、构建、测试及依赖/密钥/镜像扫描，生成版本化交付记录；启用受控 Dump 与按需诊断流程并演练常见告警处置。

验收：单节点故障后在约定恢复时间内恢复服务，未完成指令和批次可恢复；依赖故障不造成无限积压；普通看板用户无法下发或越权读取报文；发布回滚保留数据及幂等语义。

## 9. 阶段 F：完整链路压测与上线验收

优先级 P1。所有生产候选版本必须提供可复查的测试证据。

- [ ] F1：为 DeviceSocket 自身增加正式场景和业务 API/事件结果验证，不能把 Gather.TcpCenter 压测或百万设备哈希分布测试视为本服务容量证明。
- [ ] F2：执行 10,000 → 30,000 → 50,000 → 80,000 → 100,000 分阶段测试，每级覆盖连接、心跳、上报转发、可靠问答和生产日志/OTel。
- [ ] F3：覆盖三种模式 × 单条/同设备批量/跨设备批量；测试同时间批次洪峰、未来预约容量、热点设备、慢应答、重试、取消与部分失败。
- [ ] F4：满目标连接下执行 24～72 小时长稳，并同时开启看板刷新、设备查询、日志检索、历史清理和业务结果投递，检查各资源趋势。
- [ ] F5：注入 Gateway/Silo/SQL/业务下游故障，回包投递中断、网络分区、集中重连、磁盘满和 Collector 故障，验证恢复与有界退化。

### 首期发布门槛

1. 六种发送组合和单设备一问一答有端到端验证，受理/发送/确认/业务完成语义一致。
2. 每条已可靠受理指令与批次可恢复、可查询、可过期收敛；明确在途命令取消和非幂等重试边界。
3. 设备上报、应答和业务结果回传均有持久化/重投/拒绝策略及故障证据。
4. 独立看板可查看在线数、Socket 数、分类积压、各阶段命令速度、设备节点归属、单设备日志和批次进度。
5. 路由与本地连接能对账恢复，业务身份、内部 RPC、管理查询和运维操作具有相应权限。
6. 在目标硬件、约定业务流量与故障场景下完成八万/十万验收；容量结论不只依据连接数量或内存表行数。
7. 延迟、成功率、过期收敛、故障恢复、看板新鲜度和资源水位的具体门槛在正式测试前冻结，并写入验收配置和报告。
8. 格式、构建、两套测试、真实存储集成测试和相关部署验证通过，迁移/备份/回滚/故障处理 Runbook 完成演练。
