# DeviceSocket 生产化改造计划

## 1. 文档目标

本文档用于把当前通信 Demo 演进为可生产部署、可持续运维的设备接入系统。改造范围覆盖 Gateway、Orleans Cluster、MagicOnion 内部调用、协议处理、可靠消息、日志监控、部署测试和安全治理。

当前主链路统一为：

```text
设备 ──376.1 / 645 TCP──> Gateway
                              │
                              ├── Orleans Client ──> Cluster Silo
                              │                         │
                              └<── MagicOnion Unary ───┘

业务服务 ── Orleans Client ──> IDeviceGrain
```

业务服务直接调用 `IDeviceGrain`，不再设置独立 CommandCenter 服务。真实 Socket 仅保存在 Gateway 本机；Orleans 只保存设备路由、网关租约和可靠消息等可序列化状态。

## 2. 当前基线

已经具备：

- Q/GDW 376.1-2012 和 DL/T 645-2007 基础拆包、校验与错误隔离；
- 376.1 登录、退出、心跳、链路确认和 645 首帧设备绑定；
- 本机在线设备注册表、重复登录替换和 SessionEpoch 路由围栏；
- 普通消息与可靠消息两类 `IDeviceGrain` 下发入口；
- 可靠消息的 MsgId、到期、重试、取消和确认状态机；
- Gateway 进程内 `MsgId + AttemptNo` 幂等；
- 程序日志、设备上行日志和设备下行日志独立分流，固定模板使用编译时源生成；
- 心跳日志默认关闭，并支持按设备热开启或按设备稳定采样；
- 进程级连接限制，以及连接、发送积压、日志缓冲、CPU、内存、GC 和线程池观测指标；
- Windows 协议调试工具和设备模拟器。

当前限制：

- Orleans 使用本机单 Silo、内存 Grain Storage 和内存 Reminder；
- API、Swagger 和 MagicOnion 尚未配置生产认证与 TLS；
- 协议响应尚未关联到可靠消息的 `ConfirmAsync`；
- 路由事件允许丢弃，且没有持久化 Outbox 和周期性对账；
- 没有完整健康检查、OpenTelemetry、集中告警和生产部署资产；
- 现有测试以单元测试为主，尚未验证重启、故障切换和 6 万连接长稳运行。

## 3. 生产语义约束

### 3.1 可靠消息

系统对重要消息提供“持久化受理、至少一次尝试、状态可查询、到期停止、支持设备确认”的能力，不承诺跨进程故障下的物理绝对一次写入。

出现“Gateway 已写入 Socket，但在返回结果前进程退出”时，发送方无法判断设备是否收到。此时必须通过以下措施处理重复风险：

- 调用方重试始终复用原 MsgId；
- Gateway 和设备侧尽可能按业务流水号幂等；
- 协议支持查询或确认时，优先查询设备状态后决定是否重发；
- 协议无法携带业务流水号时，按设备、指令类型、协议序号和有效时间窗限制重复执行。

### 3.2 在线状态

本地 Socket 注册表是当前 Gateway 的事实来源，Orleans 路由是跨节点下发索引。两者允许短暂不一致，但必须通过租约、SessionEpoch 和周期性对账最终恢复。

### 3.3 日志

设备通信日志用于审计和故障定位，不承担可靠消息状态存储。通信链路不能因为磁盘缓慢而阻塞，但日志丢弃、磁盘不足和 Sink 异常必须产生可监控指标与告警。高频心跳默认在原始报文字符串生成前过滤，排障时按设备临时开启。

## 4. 改造阶段

### 阶段一：连接重连和路由一致性

> 2026-08-08 已完成 TCP 连接层第一批治理：登录/空闲超时、连续非法报文阈值、重复登录旧 Session 关闭、退出登录断链、TCP KeepAlive、分层接入限制和有界顺序化发送。配置、指标和边界见 `tcp-connection-layer.md`。分区路由队列、路由对账及 Gateway 排空状态仍待实施。

#### 改造内容

1. 新 Session 替换同设备旧 Session 后，由 Gateway 主动关闭旧连接。
2. 增加登录超时、空闲连接超时和连续非法报文阈值。
3. 对连接建立速率和单 IP 连接数设置可配置限制，避免重连风暴压垮进程。
4. 路由队列增加明确的丢弃回调、积压指标和事件类型统计。
5. 登录事件不允许静默丢弃；心跳事件允许按设备合并，只保留最新时间。
6. 路由事件按 DeviceId 分区顺序消费，避免单个 Orleans 故障请求阻塞所有设备。
7. Gateway 定期把本地在线快照与 Orleans 路由进行对账，修复丢失的登录、心跳和断开事件。
8. Gateway 停止时先标记节点为 Draining，再停止接收新连接、排空路由队列并关闭 Socket。

#### 交付物

- 重复登录旧 Session 关闭机制；
- 登录和空闲超时配置；
- 分区路由队列与路由对账 Worker；
- Gateway 节点 `Starting/Ready/Draining/Stopped` 状态；
- 重连、旧连接迟到事件和队列满测试。

#### 验收标准

- 同一 DeviceId 最终只有一个可下发 Session；
- 旧 Session 的迟到心跳和关闭事件不能覆盖或删除新路由；
- 人为丢弃路由事件后，对账周期内可自动恢复；
- Orleans 暂停后恢复，在线设备无需全部重连即可重新建立路由；
- 集中重连时进程不崩溃，连接拒绝、排队和恢复数量可观测。

### 阶段二：Orleans 持久化与高可用

#### 改造内容

1. 生产环境使用至少两个 Silo，开发环境继续保留本机单 Silo 配置。
2. 选定 SQL Server 或 PostgreSQL 作为首个生产存储实现。
3. 将集群成员、`DeviceStore`、`GatewayStore`、`CommandStore` 和 Reminder 全部切换到持久化提供程序。
4. 为 Grain 状态增加版本字段、向后兼容规则和数据迁移脚本。
5. 配置数据库连接池、命令超时、重试、熔断和容量告警。
6. 建立数据库备份、恢复和故障切换流程。
7. 为生产环境校验 ClusterId、ServiceId、Silo/Gateway 端口和节点身份，禁止默认本机配置启动。

#### 交付物

- `Development` 与 `Production` 分离配置；
- Orleans ADO.NET 集群和存储配置；
- 初始化及升级脚本；
- 双 Silo 部署模板；
- 状态备份恢复手册。

#### 验收标准

- 任意单个 Silo 退出不影响 Cluster 对外服务；
- 全部 Silo 重启后可靠消息和 Reminder 可恢复；
- Gateway 重启后旧节点租约能够过期，设备重连后建立新路由；
- 数据库短暂不可用时不会造成进程崩溃或无限快速重试；
- 备份数据可在独立环境完成恢复演练。

### 阶段三：可靠消息闭环

#### 改造内容

1. 为每种需要确认的 376.1 AFN/Fn 和 645 控制码/DI 定义响应匹配规则。
2. 建立待确认索引，至少包含 MsgId、DeviceId、SessionEpoch、协议序号、指令键和过期时间。
3. 上行 Handler 匹配成功后调用 `IDeviceCommandGrain.ConfirmAsync`。
4. 明确成功确认、失败确认、无确认超时、设备重连和迟到确认的状态转换。
5. Gateway 幂等记录增加设备、协议和报文摘要校验，拒绝相同键对应不同内容。
6. 为重要消息提供状态查询、取消、人工重试和失败原因查询能力。
7. 对 Expired、Failed 和确认匹配失败消息建立死信记录和人工重放流程。

#### 交付物

- 376.1/645 响应关联接口和首批实现；
- 待确认索引；
- 指令状态查询与取消接口；
- 死信和重放管理能力；
- 可靠消息端到端测试。

#### 验收标准

- 同一 MsgId 重复提交相同内容返回原状态，不产生新的业务指令；
- 同一 MsgId 更换设备、协议或报文时明确拒绝；
- 收到成功确认后停止重试并进入 `Confirmed`；
- 失败确认和无确认按照策略重试，到期后停止；
- Gateway 或 Silo 在发送链路任意位置退出后，消息状态可恢复且重复风险有明确记录。

### 阶段四：安全治理

#### 改造内容

1. 管理 HTTP API 接入 JWT/OIDC 认证和 RBAC 授权。
2. 指定设备下发、在线设备查询、原始报文查询分别设置权限。
3. MagicOnion 使用 HTTPS，并采用 mTLS 或服务身份令牌认证。
4. Swagger 只在 Development 启用，或在生产环境强制认证。
5. 设置 HTTP 请求体大小、调用频率和并发限制。
6. 设备侧增加白名单、设备档案或协议允许范围校验；无法认证的旧设备通过专用网络隔离。
7. 密钥和连接字符串通过环境变量或密钥管理系统注入，禁止进入仓库和日志。
8. 对 RawHex、设备地址和运维操作设置访问控制、脱敏与保留周期。

#### 验收标准

- 未认证调用方不能访问管理数据或执行下发；
- 非授权业务服务不能调用 Gateway MagicOnion；
- 生产环境没有明文内部 RPC；
- Swagger、日志文件和诊断接口不能被公网直接访问；
- 安全扫描不包含明文密钥和高危依赖漏洞。

### 阶段五：可观测性和运维

#### 改造内容

1. 增加 `/health/live` 和 `/health/ready`，分别表示进程存活与可接收业务。
2. Readiness 检查 TCP 服务、Orleans、路由队列、存储、MagicOnion 和日志磁盘状态。
3. 接入 OpenTelemetry，统一日志、指标和 TraceId。
4. 导出 Prometheus 指标并建立 Grafana 面板。
5. 监控在线连接、登录/断开速率、路由积压、收发速率、协议错误、RPC 延迟、可靠消息状态和日志丢弃。
6. 采集 .NET GC、堆内存、线程池、CPU、Socket 和文件句柄指标。
7. 接入集中日志平台，并为日志丢弃、磁盘不足、重试激增和确认率下降设置告警。
8. 配置崩溃 Dump 和按需 dotnet-monitor 诊断流程。

#### 验收标准

- 负载均衡器只向 Ready 节点转发管理和 RPC 请求；
- 任一跨服务下发可通过 TraceId 追踪到 Socket 写入结果；
- 路由事件丢弃、设备通信日志丢弃和可靠消息过期均可告警；
- CPU、内存或线程池异常时能够从面板定位时间点和关联流量。

### 阶段六：上报业务异步化

#### 改造内容

1. 协议 Handler 只完成协议校验、标准化和必要的即时确认，不同步执行耗时业务。
2. 标准化上报事件包含 MsgId、TraceId、DeviceId、协议、指令键、发生时间、原始报文和结构化数据。
3. 使用数据库 Outbox 保证标准化事件与投递状态可恢复。
4. 后台发布到 Kafka，业务服务按主题消费。
5. 定义事件 SchemaVersion、兼容规则、消费幂等键和分区键。
6. 建立发布失败重试、死信、查询和人工重放能力。

#### 验收标准

- Kafka 暂停不会阻塞 TCP 收包线程或导致 Gateway 内存无限增长；
- Gateway 重启后未发布的 Outbox 事件能够继续发送；
- 重复消费不会产生重复业务结果；
- 单个业务消费者故障不会影响设备登录、心跳和其他消费者。

### 阶段七：性能优化与容量验证

#### 改造内容

1. 已完成：PipelineFilter 先从 `SequenceReader` 探测精确帧长，半包不复制，完整后只复制当前帧。
2. 已完成 Raw 完整帧二次复制、单条上行 Hex 复用、心跳日志生成前过滤、按设备热开启和稳定采样。
3. 已完成：复用 SuperSocket 单连接发送锁，并保留 Gateway 单 Session、全局有界背压和发送超时。
4. 校验 SuperSocket、Kestrel、Orleans、gRPC 和数据库连接池参数。
5. 建立分阶段压测：连接建立、登录、心跳、上报、普通下发、可靠下发和集中重连。
6. 按 `docs/operations/linux-single-node-load-test.md` 在目标 8 核 16 GB 主机分阶段执行 10,000、30,000、60,000 和 80,000 连接长稳与故障注入测试。

#### 重点指标

- 当前 TCP 连接数、认证设备数和连接拒绝数；
- 每秒登录、心跳、上报和下发数量；
- P50/P95/P99 登录、路由同步和下发延迟；
- CPU、工作集、托管堆、GC 暂停和线程池排队；
- 路由队列、日志队列、Outbox 和 Kafka 积压；
- 协议错误率、发送失败率、重试率、确认率和过期率。

#### 验收标准

- 60,000～80,000 长连接达到各阶段约定稳态时间，进程无崩溃、OOM 和持续内存增长；
- 达到连接上限时新连接被有序拒绝，已有连接继续工作；
- 集中重连后在线数量和 Orleans 路由最终一致；
- 日志或业务下游变慢时通信链路保持有界内存；
- 压测报告记录软件版本、配置、报文模型、指标、瓶颈和结论，可重复执行。

### 阶段八：交付与发布治理

#### 改造内容

1. 建立 CI，执行格式检查、Release 构建、单元测试、集成测试和覆盖率检查。
2. 增加依赖漏洞、许可证、密钥和容器镜像扫描，并生成 SBOM。
3. 建立 Docker 镜像和生产部署模板，进程使用非特权用户运行。
4. 使用版本化配置、数据库迁移和向后兼容的 Orleans/MessagePack 契约。
5. 支持滚动升级、节点排空、快速回滚和版本混跑验证。
6. 编写启动、停止、扩缩容、备份恢复、故障处理和告警 Runbook。

#### 验收标准

- 仓库中不存在未纳入构建的失效工程；
- 每次合并都能自动构建并完成测试和安全检查；
- 新版本可滚动发布，已有设备连接按排空策略迁移；
- 回滚不破坏 Grain 状态、数据库结构和 RPC 契约；
- 值班人员能够仅依赖 Runbook 完成常见故障处置。

## 5. 测试矩阵

生产发布前至少覆盖以下场景：

| 类别 | 场景 |
| --- | --- |
| 协议 | 半包、粘包、垃圾前导、非法长度、校验失败、超大帧、分帧、迟到响应 |

| 性能 | 60,000～80,000 连接分阶段长稳、批量登录、心跳峰值、上下行峰值、集中断线重连 |

## 6. 实施顺序与发布门槛

推荐严格按照以下顺序实施：

1. 连接重连和路由一致性；
2. Orleans 持久化与多 Silo；
3. 可靠消息确认闭环；
4. 安全、健康检查和可观测性；
5. 上报 Outbox/Kafka；
6. 性能优化和 60,000～80,000 连接分阶段验证；
7. CI/CD、滚动发布和运维手册。

满足以下条件后，项目才能从 Demo 标记为生产候选版本：

- 生产环境不使用内存 Grain Storage 或内存 Reminder；
- 关键下发具备持久化、状态查询、确认、到期和人工处置闭环；
- 路由事件丢失后能够自动对账恢复；
- 管理 API 和内部 RPC 已认证、授权并加密；
- 具备健康检查、核心指标、链路追踪和可执行告警；
- 完成重启、故障切换、数据恢复和 60,000～80,000 连接分阶段压测；
- CI 对全部有效工程执行构建、测试和安全检查；
- 发布、回滚和常见线上故障有经过演练的 Runbook。
