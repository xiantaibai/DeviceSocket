# DeviceSocket 通讯服务中心项目背景

更新日期：2026-09-07。

本文是通讯服务中心的目标和职责基准。文中的监控看板、统一 HTTP 接口、跨设备批次和消息转发机制属于规划能力，不代表当前已经实现。当前实现与实施顺序见 [生产化改造计划](production-readiness-plan.md)，已有 Grain 和持久化机制见 [集群与可靠命令架构](cluster-and-rpc.md)。

## 1. 服务定位与容量目标

DeviceSocket 定位为设备与业务系统之间的通讯服务中心，主要承担设备消息上行转发和业务指令下行投递，并提供通讯过程的调度、跟踪、监控与故障恢复。

首期生产验收目标为系统总在线 80,000～100,000 台设备。Gateway 与 Silo 按各自负载独立扩展；单 Gateway 的连接配额由目标机器上真实混合负载测试确定。当前 85,000 的进程连接上限是已有配置，不是十万连接的验证结论。百万设备属于后续扩展方向，不作为首期已具备能力。

容量验收同时约定设备数、心跳周期、上报速率、指令受理速率、实际发送速率、应答时延、重试比例、批量峰值和故障恢复时间。设备在线数不能替代指令吞吐或 SQL 容量指标。

## 2. 职责边界

| 参与方 | 负责内容 | 边界 |
| --- | --- | --- |
| 通讯中心 Gateway | TCP 连接、登录与心跳、协议编解码和校验、真实 Socket 收发、会话替换、响应关联 | 只持有本机 Socket；协议 Handler 处理协议行为与标准化，不执行计费、订单或业务规则 |
| 通讯中心 Cluster | 设备路由、节点租约、设备级串行执行、可靠指令持久化、发送时机、超时过期、重试取消和故障恢复 | 下发统一经过 `IDeviceGrain`；不新增独立于现有 Grain 的另一套命令状态机 |
| 通讯中心上行转发模块 | 设备上报和命令结果的标准化、业务系统路由、持久化暂存、投递确认、重投和死信 | 只对通讯事件的转发负责；业务消费结果由业务系统负责并按事件身份去重 |
| 通讯中心接入与查询 API | 业务身份验证、单条/批量受理、设备定位、状态/日志查询、授权取消 | API 通过既有设备入口调度，不直接定位 Socket 后绕过命令约束 |
| 通讯中心独立监控看板 | 集群/节点/设备/命令/批次的运行情况、日志检索和告警定位 | 具有独立访问入口和发布能力，通过聚合查询与指标读取数据，不承担业务规则或消息调度 |
| 业务系统 | 决定向谁发送什么指令、何时发送，消费设备数据和结果，执行计费、分析、工单等业务 | 提供稳定幂等身份和授权目标；业务周期性采集任务由业务系统生成本次发送请求 |

通讯中心允许适度的协议结构化转换，但保持原始报文、协议版本和匹配依据可追溯。未知业务指令是否允许透传由协议能力和授权策略明确决定；未知响应不能当成成功应答。

## 3. 双向通讯闭环

### 3.1 设备消息上行

目标流程：设备 → Gateway 校验/标准化 → 持久化转发记录 → 业务投递适配器 → 业务系统。

1. 登录和心跳的必要协议响应由 Gateway 及时完成；需要转发的设备数据进入独立有界处理通道。
2. 标准事件包含 `EventId`、`SchemaVersion`、`MsgId`、`TraceId`、`DeviceId`、`Direction`、协议、指令键、Gateway/Session/SessionEpoch、接收时间，以及按策略保存的原始报文和结构化数据。这里的 EventId 是通讯事件唯一身份，与 ILogger 固定日志模板的 EventId 编号分别定义和映射。
3. 命令应答沿用对应下发的 `MsgId` 和 `TraceId`；主动上报创建自己的消息身份。`EventId` 区分同一命令下的多次事件，`Direction` 区分上下行，不因方向创建 `ParentMsgId`。
4. 按已授权的业务系统和事件类型选择目的地。队列协议与 HTTP 等投递方式由适配器隔离，在接入契约阶段确定首期实现，不把 Kafka 视为唯一前提。
5. 需要可靠转发的事件先持久化再发布，以至少一次投递、业务消费去重实现恢复。明确“已收到”“已持久化”“已转发”“业务已确认”的差别。
6. 业务下游或持久化存储故障时，缓冲、磁盘额度、接入背压和拒绝策略必须有界且可观测。业务确认型协议在持久化失败时不得仍宣称可靠受理；不能控制重发的设备需明确可能丢失的边界并产生记录与告警。

### 3.2 业务指令下行及结果回传

目标流程：业务系统 → 接入 API/Orleans 契约 → `IDeviceGrain` → `IDeviceCommandGrain` 持久化 → 调度器 → 当前 Gateway → 设备 → 应答关联 → 命令状态与结果持久化 → 原业务系统。

- 需要一问一答的业务指令统一走可靠入口，受理、等待发送、写入 Socket、收到协议确认和业务结果可用分别记录。
- 单设备最多一条业务指令占用等待应答通道；不同设备可以有界并行。同一设备的立即、延后、定时和批量请求共用此通道。
- 普通 `SendBestEffortMessageAsync` 仅提供不持久化、不自动重试的即时尽力发送；不能用它实现延后或定时可靠任务。
- 全链路复用 `MsgId`、`TraceId`，每次尝试记录 `AttemptNo`。结果不确定与明确失败分开处理；非幂等控制指令需单独定义重发或查询策略。
- 结果持久化和结果投递记录需原子关联或具有可证明的补偿机制，避免设备已确认但业务系统永远收不到结果。
- 命令取消或过期只阻止后续发送；已经写入 Socket 的指令可能已被设备执行，接口和看板必须保留在途或结果不确定信息。

## 4. 单条和批量发送模式

首期的“定时发送”指指定绝对时间执行一次。每日/每周等循环计划属于业务任务编排，若后续要求由通讯中心托管，需另行定义时区、漏执行、暂停和每次执行身份，不混入本期一次性定时语义。

| 发送模式 | 单条指令 | 批量指令 | 时序规则 |
| --- | --- | --- | --- |
| 立即 `immediate` | 受理持久化后立即具备发送资格 | 同设备逐条执行，跨设备按并发/速率限额展开 | 不保证抢占设备当前指令；实际发送还受设备在线、队列和系统容量影响 |
| 延后 `delayed` | 从首次受理时间增加指定延迟 | 以批次首次受理时间计算统一到期时刻，子项展开不能重新计时 | 持久化计算后的绝对 `NotBefore`，重试提交或服务重启不重新延后 |
| 定时 `scheduled` | 指定带 UTC 偏移的时间 | 到时后有界展开/执行批次，子项保留同一目标时刻 | 存储统一使用 UTC；不提前发送，拥塞造成的延迟需要展示与告警 |

批量同时覆盖“一台设备多条命令”和“多台设备多条命令”。同设备按可执行时间、优先级和设备内顺序号选择，不抢占正在执行的命令；未来指令不阻塞已经具备资格的指令。

### 4.1 统一接口草案

下列是待实现的 HTTP 契约草案，不能作为现有接口调用。两种受理入口通过 `schedule.mode` 覆盖六种组合，避免维护六套不同的调度逻辑。HTTP 端点继续通过对应宿主的 `DeviceApiEndpoints` 维护；Orleans 和 MagicOnion 契约分别留在既有 Contracts 项目。

| 方法与路径 | 行为 |
| --- | --- |
| `POST /api/v1/devices/{deviceId}/commands` | 单条可靠指令；支持立即、延后、定时；成功持久化后返回 MsgId、受理状态、实际 NotBefore、ExpiresAt 和查询地址 |
| `POST /api/v1/command-batches` | 同设备或跨设备批量可靠指令；返回 BatchId、批次受理状态及查询地址，通过分批查询返回子项结果 |
| `GET /api/v1/commands/{msgId}` | 命令状态、应答结果、尝试历史、排队/发送/应答时间和稳定错误码 |
| `POST /api/v1/commands/{msgId}/cancel` | 条件取消未结束的命令；与发送/确认并发时由设备状态机裁决，返回实际结果 |
| `GET /api/v1/command-batches/{batchId}` | 批次受理、展开、执行进度、分类数量和更新时间 |
| `GET /api/v1/command-batches/{batchId}/items` | 按设备、状态、错误码游标分页查询子项，禁止返回十万条完整报文 |
| `POST /api/v1/command-batches/{batchId}/cancel` | 停止继续展开并取消尚可取消的子项，返回已完成、已取消、在途和无法取消的数量 |

新接入 API 的规划字段如下。它们是 API 请求字段，不是本次新增的应用配置；正式实现时需要配套 DTO 注释、输入验证、OpenAPI 和集成测试。

| 字段路径 | 类型与规划默认值 | 约束和作用 |
| --- | --- | --- |
| `msgId` / `items[].msgId` | 必填字符串；无默认值 | 单条逻辑命令的全局幂等键；同一键不能变更设备、报文和执行策略 |
| `batchId` | 批量必填字符串；无默认值 | 批次受理幂等键；重复请求返回原批次，不能重复展开 |
| `items[].itemId` | 批量必填字符串；无默认值 | 批次内稳定且唯一，和原输入顺序一起持久化；用于断点展开、子项查询和错误定位 |
| `items[].deviceId` | 批量必填字符串；无默认值 | 子项目标设备；单条接口从 URL 取得；不把同一地址帧原样复制到不同设备 |
| `protocol`、`payload` / 子项同名字段 | 必填字符串；无默认值 | 指定协议及约定编码的单条完整帧；契约阶段固定编码，执行前校验帧内地址和协议能力 |
| `schedule.mode` | 必填枚举：`immediate`、`delayed`、`scheduled`；无默认值 | 批量首期为批次级统一模式；每个子项取得持久化后的同一调度基准 |
| `schedule.delaySeconds` | 可空正整数，单位秒；默认 null | 仅 delayed 必填，至少 1；其他模式必须缺省；最大延后时长在接口上线前固化为受校验的服务限额 |
| `schedule.executeAt` | 可空带 UTC 偏移的时间字符串；默认 null | 仅 scheduled 必填，首次受理时必须晚于服务端当前时间；其他模式必须缺省；拒绝无时区时间，最大提前预约时长受限 |
| `expiresAt` | 可空带 UTC 偏移的时间字符串；默认 null | 明确绝对截止时间，必须晚于计算后的 NotBefore；与 ttlSeconds 显式传入互斥 |
| `ttlSeconds` | 可空正整数，单位秒；未传 expiresAt 时规划默认 300 | 从本次计划发送时刻起计算截止时间，包含通道排队、重试和等待回复，不能每次重试刷新；零值非法，最大值受服务限额控制 |
| `responseTimeoutSeconds` | 可空正数，单位秒；默认使用 Silo 配置，当前为 10 | 单次写入完成后的应答窗口，实际截止时间不超过 ExpiresAt；零或负值非法 |
| `maxAttempts` | 非负整数；默认 0 | 0 表示使用 Silo 配置，当前为 5；正数包含首次正式尝试，最大值由服务限额校验 |
| `priority` | 整数；默认 0 | 数值越大越优先，仅影响同设备具备执行资格的等待项；需限制授权范围和防止长期饥饿 |
| `traceId` / 子项同名字段 | 可空字符串；默认由入口创建有效 W3C TraceId | 提供时必须校验格式；整条命令沿用同一 TraceId；批次只保存子命令关联，不为十万设备维持一个长期运行的 Span |

时间字段在首次受理时计算并持久化。相同 MsgId/BatchId 重试先进行授权和幂等内容核验，再返回原受理结果，不重新计算延后时间、TTL 或子项身份。明确传入的截止时间、模式、参数及报文均纳入幂等内容检查。

当前直接调用 Orleans 的 `ReliableDeviceMessage.ExpiresAt=null` 仍使用“受理后默认五分钟”的已有行为；新 API 应把计算后的 NotBefore 和 ExpiresAt 显式传入，不隐式改变旧调用方的默认语义。这样明天执行的指令不会在今天受理五分钟后提前过期。

### 4.2 批次与受理语义

- 单条 HTTP `202 Accepted` 表示可靠子系统已经持久化受理，不表示已经发送或设备执行成功。
- 批次 `202 Accepted` 表示批次清单和恢复游标已持久化，不表示所有子项都已被设备命令子系统受理。看板分开展示“清单已接收”“子项展开/受理”“实际发送”“应答完成”。
- 批次按固定大小分块和全局并发/速率预算展开，采用逐项结果语义。支持部分成功；请求整体格式错误与子项业务拒绝分别返回，已受理子项不能因其他项失败而重复执行。
- 同设备子项复用 `SendReliableMessagesAsync` 的串行语义；跨设备新增批次协调和持久化查询记录，不能把十万条任务一次性放入内存或无界 `Task.WhenAll`。
- 所有模式在失败恢复后，未到 NotBefore 的继续等待；已经到时但未过期的可按限额继续；已经过期的必须进入终态，不补发。
- 请求条数、总字节数、每设备待处理数、未来预约数、单业务系统和节点配额均需在契约冻结时给出明确上限、拒绝码和重试建议。

## 5. 独立监控看板

看板是通讯中心的正式交付物，具有独立访问入口、登录权限和发布能力。基础设施时序图可嵌入或跳转到监控平台；设备归属、单设备指令日志和批次进度需要专门的业务查询页面，不能只交付 CPU/内存图表。

| 页面 | 必须展示的内容 |
| --- | --- |
| 集群总览 | 在线设备数、Socket 连接数、未认证连接数、可用节点数、队列积压、指令各阶段速度、成功/超时/过期率、告警和数据更新时间 |
| Gateway 节点 | NodeId、InstanceId、地址、版本、Starting/Ready/Draining/Stopped、租约、节点在线数/Socket 数、连接上限、CPU/内存/GC/FD、收发速率 |
| Silo 与调度 | Silo 状态、Grain 活跃情况、调度延迟、待发送/预约/等待应答/重试数量、SQL 耗时、恢复和清理进度 |
| 设备列表与详情 | 按 DeviceId、协议、在线状态、Gateway 筛选；当前 Gateway/实例、SessionId/SessionEpoch、地址、上线/最后活动/租约时间、当前指令和等待数量 |
| 单设备指令日志 | 按时间、方向、MsgId、TraceId、指令类型、状态查询；上下行报文、尝试次数、发送/应答时刻、协议错误和历史节点，敏感字段按权限展示 |
| 命令详情 | 受理→计划时间→排队→每次发送→设备应答→终态→业务结果投递的时间线，显示各段耗时与结果不确定原因 |
| 批次详情 | 模式、目标时间、总数、展开/受理/拒绝/成功/失败/过期/取消/进行中数量、速率、子项分页与取消进度 |
| 上行转发与告警 | 业务系统投递速度、待转发/重投/死信数量、最老等待时间、业务确认状态，以及路由、日志和 OTel 导出异常 |

“设备在哪个服务”默认指真实 Socket 所在的 Gateway NodeId + InstanceId；Silo 激活位置可作为诊断信息，但不能代替真实连接归属。设备迁移后保留指令当时所在节点，防止只用当前节点检索遗漏历史日志。

看板配套查询接口同样属于草案：

| 方法与路径 | 查询范围 |
| --- | --- |
| `GET /api/v1/monitoring/overview` | 集群汇总指标、时间范围和数据新鲜度 |
| `GET /api/v1/gateways` | 节点状态、容量与租约，按状态游标分页 |
| `GET /api/v1/devices` | 按设备编号、协议、Gateway、在线状态游标分页检索 |
| `GET /api/v1/devices/{deviceId}/route` | 当前 Gateway/实例/Session 与路由校验时间 |
| `GET /api/v1/devices/{deviceId}/commands` | 指定时间窗口内的指令历史与状态，游标分页 |
| `GET /api/v1/devices/{deviceId}/traffic` | 指定时间窗口内的上下行通讯日志，支持 MsgId/TraceId 筛选、分页与报文权限控制 |

看板命令和批次详情复用前述查询契约。所有查询先校验业务归属和访问权限；不存在、无权访问和数据源不可用分别采用一致的对外错误规则，避免通过设备枚举泄露授权范围外的数据。

### 5.1 指标口径

| 名称 | 统一定义 |
| --- | --- |
| Socket 连接数 | 当前各 Gateway 真实 TCP Session 总数，包含未认证连接和替换过程中尚未关闭的旧连接 |
| 在线设备数 | 按 DeviceId 去重、当前 Session 有效且 Gateway/路由租约有效的设备数；同时展示本地认证数与集群路由数的差值 |
| 队列积压 | 分开展示路由同步、上行转发、已具备资格待发送、未来预约、等待应答、重试等待、回包重投和日志缓冲，不合并成一个无法解释的数字 |
| 命令速度 | 分别计算受理条/秒、物理发送尝试次/秒、协议确认条/秒、业务结果完成条/秒；批次不按一次 HTTP 调用算一条指令 |
| 命令延迟 | 分别记录计划到实际开始的调度延迟、通道排队、Socket 写入、设备应答和端到端耗时；展示 P50/P95/P99 |
| 成功率 | 按逻辑命令去重统计，重试不重复计为受理；协议确认、业务结果成功与转发确认分别统计，排除条件在面板标明 |
| 数据新鲜度 | 每个聚合结果携带采集/更新时间和来源状态；节点失联时显示失联/数据过期，不能显示为零负载或正常 |

聚合指标通过 OTel/时序存储读取，设备路由和命令历史通过可索引查询模型读取，原始报文从通讯日志或归档读取。看板刷新不得逐一激活十万个 Grain，也不得全量拉取在线表或报文。设备详情允许定向校验实际路由。

采集和刷新频率由容量测试确定并配置化；高基数 DeviceId/MsgId/TraceId 留在查询、日志和 Trace 中，不作为时序指标标签。查询本身具备分页、时间窗口、限流和独立资源预算。

## 6. 首期交付范围

1. 设备上报转发、业务指令下发和指令结果回传三条通讯链路，以及明确的受理/投递/执行语义。
2. 单条与批量的立即、延后、定时接口；同设备一问一答、超时过期、失败恢复、查询和取消。
3. 独立监控看板、查询 API、集中通讯日志、OpenTelemetry 指标/追踪和可执行告警。
4. 多 Gateway/Silo、路由对账、容量配额、节点排空与故障恢复。
5. 当前 DeviceSocket 完整链路的 80,000～100,000 台混合负载与长稳验收，发布和回滚手册。

以上能力按 [生产化改造计划](production-readiness-plan.md) 分阶段落实。业务周期任务、业务报表和长期业务数据分析保持在业务系统；通讯中心按约定保留可追溯的通讯记录和投递结果。
